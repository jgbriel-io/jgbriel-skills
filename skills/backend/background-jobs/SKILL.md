# Background Jobs

## Principle

If the work does not need an immediate answer for the user, it must not block the
request. Sending an email, generating a report, charging a card, syncing with an
external service — all of it becomes a queued job rather than a synchronous call
inside the HTTP handler.

```
// ❌ The request waits for the heavy work
handler(req):
  sendWelcomeEmail(user)       // slow network call
  generateInvoicePdf(order)    // CPU-bound
  return 200(order)

// ✅ The request enqueues and answers immediately
handler(req):
  queue.enqueue('send-welcome-email', { userId: user.id })
  queue.enqueue('generate-invoice', { orderId: order.id })
  return 202(order)
```

Rule of thumb: if the operation can fail because of an external system, takes more
than about a second, or does not affect the response the client needs now, it is a
candidate for a job.

## Anatomy of a job

| Element | Responsibility |
|---|---|
| Producer | Enqueues the job with a minimal payload — ids, not whole objects |
| Queue/broker | Stores, orders and distributes to workers |
| Worker/consumer | Processes, and decides success, retry or permanent failure |
| Dead-letter queue (DLQ) | Holds jobs that exhausted their attempts, for manual investigation |

```
// ❌ The payload carries the whole object, which may be stale when the job runs
queue.enqueue('process-order', { order: fullOrderObject })

// ✅ The payload carries a reference; the worker loads current state
queue.enqueue('process-order', { orderId: order.id })
```

## Idempotency

A job can run more than once: the broker redelivers on timeout, a worker crashes
after processing but before acknowledging, someone retries by hand. Processing the
same job twice must not double its effect.

```
// ❌ Running twice charges the customer twice
function processPayment(job):
  charge(job.customerId, job.amount)

// ✅ An idempotency key makes the effect happen once
function processPayment(job):
  if paymentLedger.exists(job.idempotencyKey):
    return paymentLedger.get(job.idempotencyKey)  // already processed; return the earlier result
  result = charge(job.customerId, job.amount)
  paymentLedger.save(job.idempotencyKey, result)
  return result
```

- Every operation with an external side effect — a charge, a send, a resource
  creation — needs an idempotency key, generated by the producer rather than the
  worker.
- Persist the key durably (a table, Redis with a TTL) *before* acknowledging
  success, not after.
- Idempotency is not "do not run twice at once" — that is locking. It is "running
  N times has the same effect as running once".

## Retries and backoff

A transient failure — a network timeout, a rate limit, an external service down —
deserves an automatic retry. A permanent one — an invalid payload, a resource that
does not exist — does not: retrying only postpones the inevitable and clogs the
queue.

```
// ❌ Immediate, unlimited retry — amplifies the outage instead of easing it
function onFailure(job):
  queue.enqueue(job)  // straight back onto the queue, no limit

// ✅ Exponential backoff with an attempt limit
function onFailure(job, attempt):
  if attempt >= MAX_ATTEMPTS:
    deadLetterQueue.push(job, reason: lastError)
    return
  delay = min(baseDelay * 2 ** attempt, maxDelay) + jitter()
  queue.enqueueDelayed(job, delay)
```

- Exponential backoff plus jitter. Without jitter, every job that failed together
  retries together — a thundering herd.
- Distinguish retryable from non-retryable in the worker: a validation error or a
  4xx does not enter the retry cycle; it goes straight to the DLQ or is dropped
  with a log.
- An attempt limit is mandatory. Without one, a poisoned job reprocesses forever
  and masks the real alert.

## Dead-letter queue

Every job that exhausts its attempts goes to a separate queue rather than being
dropped silently.

- The DLQ exists for visibility and for reprocessing once the cause is fixed. It is
  not a bin.
- Alert when something new lands in it. A DLQ growing unwatched is an operational
  failure, not only a coding one.
- A job in the DLQ carries its original payload, the final failure reason and the
  attempt history. Without those, investigation becomes archaeology.

## Ordering and concurrency

- Related jobs that must run in order — events for the same order, say — go to a
  queue or partition keyed by their grouping id. Never rely on the queue's global
  ordering.
- Two workers must not process the same resource at once where the operation is
  not idempotent on its own. Use a distributed lock, or partition the queue by
  `resourceId`.
- Worker concurrency is limited on purpose. Unlimited, a queue spike takes down the
  external service the jobs call.

## Minimum observability

- Every job logs its id, type, current attempt, duration and outcome (see
  `structured-logging`).
- Queue metrics: depth, the age of the oldest job (lag), error rate, and the rate
  of items reaching the DLQ.
- A job that hangs — neither succeeding nor failing for a long time — needs an
  explicit timeout, or it occupies the worker indefinitely.

## Checklist

- [ ] Slow, external or non-critical work is queued rather than called synchronously in the handler
- [ ] Job payloads carry a reference (an id), not the whole object
- [ ] Operations with external side effects have an idempotency key persisted before success is acknowledged
- [ ] Retries use exponential backoff plus jitter, with a maximum attempt count
- [ ] Non-retryable errors (validation, 4xx) stay out of the retry cycle
- [ ] Exhausted jobs reach the DLQ with payload, reason and history — never dropped silently
- [ ] An alert fires when something new enters the DLQ
- [ ] Order-dependent jobs use a queue or partition keyed by their grouping id
- [ ] Workers have an explicit per-job timeout
- [ ] Worker concurrency is bounded

## By stack

**BullMQ (Node/TS, Redis)**
```ts
await queue.add('send-invoice', { orderId }, {
  jobId: `invoice-${orderId}`,        // idempotency: the same jobId does not duplicate
  attempts: 5,
  backoff: { type: 'exponential', delay: 2000 },
});
// after five failures the job lands in the "failed" set, monitored separately
```

**Supabase (pg_cron plus an Edge Function, no dedicated broker)**
```sql
-- pg_cron fires periodically; the function drains a queue held in a table
select cron.schedule('process-jobs', '*/1 * * * *',
  $$select net.http_post(url := 'https://<project>.supabase.co/functions/v1/process-jobs')$$
);
```
```sql
-- the queue as a table: status, attempts and idempotency_key prevent duplication
create table jobs (
  id uuid primary key default gen_random_uuid(),
  type text not null,
  payload jsonb not null,
  status text not null default 'pending', -- pending/processing/done/dead
  attempts int not null default 0,
  idempotency_key text unique
);
```

**Celery (Python, Redis/RabbitMQ)**
```python
@app.task(bind=True, max_retries=5, default_retry_delay=10)
def send_invoice(self, order_id):
    try:
        charge_and_send(order_id, idempotency_key=f"invoice-{order_id}")
    except TransientError as exc:
        raise self.retry(exc=exc, countdown=2 ** self.request.retries * 10)
```

**Sidekiq (Ruby)**
```ruby
class SendInvoiceJob
  include Sidekiq::Job
  sidekiq_options retry: 5

  def perform(order_id)
    key = "invoice-#{order_id}"
    return if InvoiceLedger.exists?(key)
    InvoiceLedger.record(key) { charge_and_send(order_id) }
  end
end
# an exhausted job lands in the Dead Set, visible in Sidekiq's UI and API
```

## Anti-patterns

- ❌ A slow or external call inside the synchronous request instead of a queued job
- ❌ A job payload carrying the whole object rather than a reference
- ❌ A side-effecting operation with no idempotency key
- ❌ Immediate retries with no backoff, or with no attempt limit
- ❌ A validation error entering the same retry cycle as a transient one
- ❌ An exhausted job dropped silently instead of reaching the DLQ
- ❌ A DLQ with no alert, so nobody notices jobs failing
- ❌ A worker with no timeout, stuck on a job that never finishes
- ❌ Unbounded worker concurrency, taking down the external service the jobs depend on
- ❌ Order-dependent jobs processed on a queue with no partitioning
